## FENZ K codes

Trucks report their status over the radio as a K code. The app shows the K code it heard on each
truck (`boardText()` in `web/src/core/derive.ts`, e.g. "K99 Well-involved fire"); the legend uses
`stateText()` ("K1 Responding"). The codes live in `statusCodes` in `data/codebook.json`,
generated by `tools/make_codebook.py` — change them there, then re-run it.

### Status

| K code | Meaning | App state (`ApplianceState`) |
|---|---|---|
| K0 | Not available | `status-unknown` |
| K1 | Proceeding to incident (responding) | `responding` |
| K2 | In attendance at the incident | `at-incident` |
| K3 | On radio, outside its normal turnout area | `out-of-area` |
| K4 | On radio, inside its normal turnout area (available) | `available-radio` |
| K5 | On radio, available at the incident | `at-incident` |
| K6 | On pager (states location) | `available-radio` |
| K7 | At its normal station | `on-station` |
| K8 | Not allocated (older lists: at residence) | not in the codebook |
| K9 | Off radio (states location) | `status-unknown` |
| K10 | Re-commissioning the appliance | `status-unknown` |
| KE | Unable to proceed (states reason) | `status-unknown` |
| K11 | Service required (states which; K11-F fire investigator, K11P police, K11P-1 police confidential) | `at-incident` |

### First arrival (sent by the first truck to arrive; everyone after sends K2)

| K code | Meaning |
|---|---|
| K55 | First appliance in attendance, special service call |
| K66 | First appliance in attendance, non-property fire (e.g. scrub) |
| K77 | First appliance in attendance, nothing showing, investigating |
| K88 | First appliance in attendance, property fire, apparently small |
| K99 | First appliance in attendance, property fire, well involved |

These are `"arrival": true` in the codebook and all set `at-incident`. The demo sends one from the
first truck at each job (mostly K77, sometimes K99).

K31–K34 are radio procedure codes (not statuses) and aren't in the codebook.

Sources: FENZ "K Codes and phonetic alphabet" sheets (22 March 2022, 1 December 2023) released under
the OIA on fyi.org.nz (requests 20111 and 25242); the community list at radiowiki.org.nz ("Fire Radio
Codes"). Some Tait selcall setups also use K7-style numbers for things like power failure, so not
every status message will be in this table.

The SelCall tones that carry each K code (the `suffix` after `-` in a 13-tone message) are
**placeholders** (`"demo": true`): "F" + the K number, padded with A0C2 (KE is `FBA0C2`). Replace
them with the real suffixes once they're confirmed from recordings.

## SelCall format (short)

- CCIR tones, E = 2110 Hz is the repeat tone.
- Station turnout: `182` + callsign turns out that truck.
- `182` + station number + `0` is just the radio's **ACK** of a turnout, a few seconds after it;
  it is not a call-out. The app reads it (so it isn't an "unknown code") but leaves it off every
  view (`useBoard` filters `station-ack`) and never alarms on it.
- Appliance message: `HEADER-SEP+BODY` (13 tones); short appliance call is header + final tone,
  and the final tone is the call type. `B` = priority call (the truck asking Comcen to respond to
  them urgently) and `C` = routine call (asking Comcen to respond when they can) are confirmed;
  `4` = turnout ack is still a guess.

## Layout and checks

- Python decoder: `selcall/`, benches in `bench/`, tests `python -m pytest tests`.
- Web app: `web/` (Vite + React + TS). `npm test`, `npx tsc --noEmit -p .`, `npm run build`.
- Deployed to GitHub Pages from `master` by `.github/workflows/pages.yml`.
- The browser decoder is WebAssembly: `web/assembly/selcall.ts` (AssemblyScript) holds the
  filter, tone detection, slot reading, tone table and the demo's tone encoder.
  `scripts/build-wasm.mjs` compiles it and embeds it as base64 in `src/decoder/wasm.gen.ts`
  (git-ignored; the `pre*` npm scripts regenerate it). `src/decoder/selcall.ts` only copies audio
  in, unpacks results and chunks long recordings. Keep it in step with `selcall/decode.py`.
  The hot loop uses raw pointers (`load<f32>`); bounds-checked access was ~3x slower.
- Production builds are also obfuscated (`javascript-obfuscator` plugin in `web/vite.config.ts`).
  `OBFUSCATE=0 npm run build` gives a readable build for debugging.
